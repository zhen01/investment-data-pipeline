# Phase 4 — SQLite materialization, lineage, backfills and CI

**Status:** Tested offline prototype, not a production trading service. All example identifiers and prices are synthetic. Existing Phase 1–3 modules remain unchanged.

## Additions

- `src/market_pipeline/storage.py`: SQLite schema for raw observation metadata, materialization runs, split-adjusted bars and row-level lineage. Content-derived run IDs support deterministic idempotent backfills; SQLite transaction protects against partial writes.
- `src/market_pipeline/backfill_cli.py`: repeatable JSON fixture ingestion, PIT security resolution, split adjustment, optional registration of previously saved SEC raw-object manifests, and machine-readable quality metrics.
- `.github/workflows/ci.yml`: pytest on Python 3.10 and 3.13 when pushed to GitHub.
- `tests/test_storage.py`: 6 integration tests for idempotence, PIT, lineage, missing identifiers, quality gates, and tamper-detection of raw bytes.
- `examples/point_in_time_backfill.json`: deterministic research-data fixture.

## Quickstart

From repo root (Python 3.10+):

```bash
python -m pip install -e '.[dev]'
python -m pytest -q
python -m market_pipeline.backfill_cli \
  --input examples/point_in_time_backfill.json \
  --db .local/research.sqlite \
  --as-of 2026-02-15T00:00:00Z \
  --reference-date 2026-02-14
```

Run that CLI command twice: the second run returns `already_materialized` with the identical run ID. Local `.local/` databases should be excluded from Git; do not commit proprietary market-feed data or EDGAR raw captures by default.

Optional raw-ingestion catalog registration (requires a manifest already written by Phase 2, and verifies the referenced payload hash):

```bash
python -m market_pipeline.backfill_cli \
  --input examples/point_in_time_backfill.json \
  --db .local/research.sqlite \
  --as-of 2026-02-15T00:00:00Z \
  --reference-date 2026-02-14 \
  --raw-store .local/edgar \
  --manifest .local/edgar/manifests/aa/<manifest-id>.json
```

The raw observation registry and adjusted-bar run are independently auditable; **there is not yet a guaranteed relational link between a particular filing and an adjusted market bar**. The example does not claim that synthetic ticker data came from SEC EDGAR.

## Measured data-quality metrics

`rows_materialized`, `unresolved_identifiers`, `identifier_resolution_rate`, `dq_errors` and `lineage_rows` are emitted for each completed run. Invalid OHLC, unknown identifiers in strict mode, duplicate post-resolution rows and future-known market bars fail closed rather than being silently dropped. `dq_errors` is zero for successful committed runs; failed attempted runs currently raise an exception rather than logging an error row.

## Boundaries

- The SQLite materializer accepts offline normalized JSON fixtures; no live licensed market feed, orchestration scheduler, or remote PostgreSQL service is configured.
- SEC raw payload registration uses manifests generated by the existing Phase 2 ingestion; it does not parse SEC data into OHLC bars. This prevents false data-source attribution.
- Immutable file storage is write-once by convention, not compliance-grade WORM; SQLite is a single-writer local database.
- The initial split-adjusted view supports splits only, not dividend/total-return adjustment, symbol history correction versions, delistings, multiple listings or merger consideration.
- Current input validation uses the prior Phase 1 validator; collisions between the same ticker on different exchanges in one batch are not supported by that validator.
- Tests are offline and deterministic. CI workflow becomes active **after the files are pushed to GitHub**.
